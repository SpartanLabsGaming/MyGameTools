The one-sentence summary

GameTools gives you a World that owns game objects, ticks them deterministically, indexes them spatially, announces what happened on an event bus, and — through gametools-net — broadcasts a serialised view of them to UDP clients; everything else in the library exists to serve one of those five verbs.

0.1The library in one page

What it is

A Kotlin/JVM engine layer for 2D multiplayer games: the plumbing every simple game needs, extracted so gameplay code can be written on top of it.

It is not a renderer, not a physics engine, and not a game loop — you supply the window, the drawing and (optionally) the clock.

What it gives you

  • A four-layer object hierarchy
  • A stat & buff system with real stacking rules
  • A quadtree broad-phase index
  • A deterministic, seeded tick
  • A typed, synchronous event bus
  • Serialisable snapshots of everything drawable
  • A UDP game server

// A complete, headless, authoritative game: one world, two units, one fight.
val world = World(seed = 42L)                       // fixed seed ⇒ reproducible run
val hero  = Alive(Point(0.0, 0.0),   Dimensions(30.0, 30.0), maxHealth = 200.0)

hero.faction = "blue"; ogre.faction = "red"
hero.speed.base = 14.0                                 // units per tick

world.events.subscribe { event ->                      // react without wiring into combat code
    if (event is GameEvent.EntityDied) println("died: " + event.entity.entityId)
}

hero issueAttack ogre                                  // close to range, then swing on a loop
repeat(600) { world.tick() }                          // you own the clock…

// …or let the library own it:
val loop = SimulationLoop(world, LoopSettings(tickRateHz = 20.0))
loop.start()

0.7What the library is actually for

GameTools exists because the same six hundred lines were being rewritten at the start of every project: a base class with a position and an update hook, a health bar that follows its owner, a stat that a potion can raise by twenty per cent, a loop that walks a list of things and calls update() on each, and a socket that squirts JSON at whoever is listening. None of that is interesting, all of it is fiddly, and every rewrite got it slightly wrong in a new way.

The library's organising idea is that a game object is not one class with forty fields but a stack of concerns, each of which can be reasoned about alone. Position and lifetime are the concern of GameObject. Being drawn is the concern of VisibleObject. Getting somewhere is the concern of Actor. Being hurt and hurting back is the concern of Alive. A projectile is an actor with a payload; a player is a roster. Nothing in the stack knows about rendering, and only one class in the whole library knows about a socket.

Around that stack sit five services. World owns objects and gives them a heartbeat. Quadtree answers "what is near here?" without scanning everything. EventBus lets the rest of your program find out what the simulation did without being welded to the code that did it. RandomSource makes every roll reproducible from a seed. GameServer puts a serialised view of the world on the network. Learn those five and the library holds no more surprises.

Two decisions colour everything that follows, and both are worth knowing before you read another page. The first is that the library never runs itself: World.tick() is called by you, or by the optional SimulationLoop, and no thread exists that you did not ask for (with the single exception of the networking layer's socket threads). The second is that fallible operations return Result rather than throwing: a step that cannot be computed, a player that is not connected, a serialisation that fails — each hands back a value you can inspect, and the simulation carries on. Together these mean a GameTools world is a plain object you can step in a unit test, one tick at a time, with nothing running behind your back.

1.7Why a hierarchy, and why this one

Inheritance has a poor reputation in game development, and deservedly so: the archetypal engine class hierarchy is a tower of half-abstractions in which Enemy extends Character extends Entity and every level adds fields that three quarters of its subclasses ignore. GameTools takes the shape anyway, but under a discipline that makes it work: each layer adds one concern, that concern is complete at its layer, and no layer knows anything about the layer beneath it.

The test to apply, when you are wondering where a new field belongs, is to ask which layer would be incomplete without it. A texture name is meaningless to something that is never drawn, so it lives on VisibleObject and not on GameObject. A destination is meaningless to something that cannot move, so it lives on Actor. Evasion is meaningless to something that cannot be hit, so it lives on Alive. Applied consistently, the rule keeps every layer small enough to hold in your head — the largest, Alive, is under five hundred lines including its documentation and its snapshot.

The pay-off is that composition still works where you want it. A decoration such as a health bar or a nameplate is not a subclass of anything; it is a plain VisibleObject in another object's subObjects list. A movement behaviour is not a subclass either; it is a Movement value assigned to a field, which means an actor can change how it moves at runtime without changing what it is. Inheritance carries the kinds of thing that exist; composition carries what they are doing right now. Nearly every extension you will write fits into one of those two slots, and the ones that fit into neither — an ability system, an inventory — belong in your game, not in the engine.

1.8The module split

Until version 3.1.0 the library shipped as one artifact. It now ships as three, and the reason is dependency weight rather than code size. A headless simulation — a unit test, an AI training harness, a server that speaks some other protocol — has no use for a UDP stack, and forcing WebTools and a socket implementation onto every consumer to hand them a Quadtree was the wrong trade.

gametools-core is therefore everything that can run with no I/O at all: the object model, the stats, the events, the spatial index and the simulation. gametools-net holds GameServer and MouseAction, depends on core with api visibility, and is the only place in the tree where a socket exists. The gametools umbrella carries no source; it exists so that an existing consumer can keep a single dependency line and receive both modules transitively, which made the split a non-breaking change for everyone who was not already reaching into internals.

Each module publishes independently to Maven Central under the same version, with its own Dokka "view source" links and its own POM description, from shared Gradle convention plugins in build-logic. Adding a fourth module — a persistence layer, say, or an AI package — means writing a four-line build file that applies gametools.published-library and declaring its coordinates; the toolchain, the dependency set, the test-level wiring and the publishing configuration all arrive with the plugin.

1.9Result instead of exceptions

A simulation that throws is a simulation that stops, and a game server that stops because one actor's destination held a NaN is not acceptable behaviour. The library's answer is to reserve exceptions for programmer error — a non-positive maxHealth, a zero tick rate, a maxDuration of zero — and to represent every runtime failure as a value.

So GameObject.distanceFrom returns Result<Double> rather than throwing on a NaN coordinate; Movement.step returns Result<Unit> so that a step which cannot be computed surfaces at the call site instead of unwinding the tick; and Actor.onUpdate logs a failed move and carries on, leaving the actor where it stands. On the networking side every send returns a Result, and GameServer.pushToAllPlayers is careful to attempt delivery to every player regardless of earlier failures, folding the outcomes so that only the reported result short-circuits, never the delivery itself.

The practical consequence for your code is that failures are visible but never fatal, and that you choose the policy. getOrDefault when a sensible fallback exists; onFailure and a log line when it does not; getOrThrow in a test where a failure genuinely is a bug.

1.10Logging

Every layer holds one slf4j logger named after its package — com.spartanlabs.gaming.gameobjects, …event, …simulation.SimulationLoop, and GameServer — and the library binds only to the facade, never to an implementation. That is deliberate: a library that ships a logging backend picks a fight with its consumer's own choice. Add Logback, or Log4j2, or nothing at all; with no binding on the classpath slf4j falls back to a no-op and the engine runs silently.

The levels are used consistently. debug carries per-tick detail — a step taken, a buff applied, an object numbered — and is expected to be off in production. info marks lifecycle events you would want in a server log: a world's seed at construction, a player joining, the simulation loop starting. warn marks a recoverable mistake in your code, such as a buff targeting a stat the object does not expose, or an angle outside 0..359 being normalised. error is reserved for a failure the engine could not absorb.

Two of those warnings are worth watching for specifically, because they indicate bugs that are otherwise silent: the "buff targets unknown stat" warning means a mod was skipped and your effect is doing nothing, and the "angle normalised" warning means somebody is doing raw angle arithmetic without wrapping.

1.11Source-file conventions

Imports in every file are grouped into numbered regions — 1. Organization Internal, 2. Intended Function, 3. Utility / Catch-all, 4. Programming Infrastructure and Support — so that the top of a file tells you, at a glance, how much of the outside world it depends on and what for. Bodies are further divided by //region markers named for the concern they hold (CAPABILITIES, BUFFS, COMBAT, DEATH, HEALTH BAR). Public API carries KDoc that documents behaviour and edge cases rather than restating the signature — the Dokka output published with each release is generated from exactly the comments you see in the source.

Snapshot types live in the same file as the type they snapshot, immediately after it, so that adding a field to a class and forgetting to add it to the wire format is a visible omission rather than an invisible one two directories away.

1.12The test hierarchy

Tests are organised by level rather than by the class under test, in packages named com.spartanlabs.gaming.testing.<level>, and each level has its own Gradle task so CI can gate them independently. Level 2 (component) tests exercise one type's business logic in isolation and make up the bulk of the suite. Level 3 (integration) tests exercise the boundary with WebTools. Level 4 splits three ways: 4a (deterministic) asserts algebraic laws — that stat arithmetic is associative, that a snapshot round-trips, that the same seed yields the same combat — while 4b (e2e) runs a real client against a real server, and 4c (non-functional) checks throughput and robustness under load.

A level with no tests in a given module is a green no-op rather than a failure, which is what lets one task span every module. The whole suite still runs from gradle test; the per-level tasks exist for the pipeline, and for the developer who wants the fast half of the suite on every save.

2.5Determinism: what is and is not promised

Promised

  • Same seed + same sequence of external calls ⇒ same result, run after run.
  • Every engine roll (today: evasion) draws from World.rng.
  • A world-less Alive falls back to a source seeded on its own entityId, so it too is reproducible.
  • Iteration order is insertion order, everywhere.
  • Event delivery order is publication order.

Not promised

  • Determinism across library versions.
  • Determinism if your code calls Math.random() or reads the wall clock.
  • Determinism under a SimulationLoop: real elapsed time decides how many ticks run, and a stall drops owed time. Drive tick() directly to replay.
  • Cross-JVM floating-point identity.
Pin the seed to reproduce a bug

Every world logs its seed at info the moment it is constructed. Copy that number out of the log, construct World(seed = thatNumber), replay the same inputs, and the failure recurs — including the evasion rolls.

2.6The world as a container

A World is five things in one object: a list of everything being simulated, a spatial index over the visible part of that list, an identity index over all of it, a bus that reports what happened, and a seeded source of randomness. It is deliberately not a sixth thing — it is not a clock. Nothing inside a world moves until something outside calls tick().

That omission is the single most important design decision in the library. A world with its own thread is a world you cannot step through in a debugger, cannot advance one frame at a time in a test, and cannot replay. A world without one is an ordinary object: you call a method, it does exactly one frame of work on your thread, and it returns. The convenience of a real-time loop is available when you want it (§2.10) but it is a separate class you opt into, and nothing in the engine depends on it existing.

The contents themselves are held in a plain, public ArrayList. That is unusual for a library API and it is intentional: the tick's rules about ordering and mid-pass mutation are stated plainly enough (§2.7) that direct access is safe, and hiding the list behind an interface would only have forced the addition of a dozen delegating methods. The cost is that gameObjects += obj bypasses the bookkeeping add() performs, which is why the quick-reference card opposite spells out what you give up.

2.7The tick lifecycle, step by step

A tick begins by incrementing tickCount, which is the number every other part of the frame can be described relative to. It is monotonic, it is 0 before the first tick, and it is the natural stamp to put on a network snapshot so a client can discard frames that arrive out of order.

Second, the quadtree is rebuilt from scratch: cleared, then re-filled with every VisibleObject in gameObjects at the position it holds at that instant. Rebuilding rather than incrementally updating is the right trade for a game where most objects move most frames — an incremental index would pay removal and re-insertion costs per moved object anyway, and it would be a subtler thing to get right. The consequence you must remember is that the index is a snapshot of the frame's opening positions: an object that moves during step 4 still appears in the tree where it started, so a neighbour query later in the same frame sees stale coordinates by up to one tick of movement. For broad-phase use this is exactly what you want — the window is generously sized and the narrow-phase check runs against live positions anyway.

Third, identity is reconciled. The id index is cleared and every object in the list is re-enrolled in list order, recursing into sub-object trees so that a health bar or a nameplate is addressable as well as its owner. An object that has no id yet is given the next one; an object that already has one keeps it. Then every top-level object that has not previously been announced raises a GameEvent.EntitySpawned, and the record of announcements is trimmed to the objects the world still owns — which is what allows an instance that leaves and later returns to be announced again.

Fourth, the objects are ticked. The pass runs over a copy of the list taken before it starts, and this is what makes mid-pass mutation safe: an object may add a projectile to the world, or queue itself for removal, without disturbing the iteration. The price is that a mid-pass addition does not tick this frame. It is numbered and announced at the top of the next tick and runs from there — one frame of latency on a spawn, in exchange for never having to reason about iterating a list that is changing underneath you.

Fifth and last, removals are drained. The queue is copied, de-duplicated, removed from the object list in one pass, and then each removed object is dropped from the id index and the announcement record and raises a GameEvent.EntityRemoved. De-duplication matters because two independent systems may queue the same dying object in the same frame; without it, the removal event would fire twice for one death.

Events are published synchronously, as they occur — an AttackLanded raised in the middle of step 4 reaches its listeners before the next object ticks, not at the end of the frame. This keeps causality legible in a log and lets a listener react before the rest of the frame is decided; the corresponding obligation is that listeners must be quick and must not mutate the world in ways the remainder of the pass would find surprising.

2.8Entity identity

Position in a list is a terrible way to refer to a game object across a network. Objects spawn and despawn constantly, every such change renumbers everything after it, and a client acting on last frame's index acts on the wrong unit. EntityId exists to fix that: a value class wrapping a Long, assigned by the owning world in acquisition order starting from 1, never changed and never reused.

Three properties are worth internalising. First, the id is per world: the same raw number in two different worlds means two different objects, so ids are safe to compare only within a world. Second, the id is sticky to the instance: re-adding an object, even to a different world, keeps the id it was first given — worth knowing if you pool and recycle objects. Third, UNASSIGNED is 0, which is also what a pre-3.1 snapshot decodes to, so "id is zero" reads uniformly as "not addressable" whether the cause is a world-less object or an old payload.

World.byId(id) returns the object or null, and the null is the point. When a client sends a command naming an entity that has since died, the right answer is not an exception but "that no longer exists" — which is precisely what a command handler wants to branch on.

2.9Adding, removing, and the removal queue

Removal is deferred rather than immediate, and always was, because the alternative is a mutation in the middle of an iteration. An object that wants to leave the world adds itself to removeList and keeps running until the end of the frame; the world drains the queue once every object has ticked. A dying Alive with the default REMOVAL death response does exactly this, which is why Alive carries a back-reference to its world at all.

That back-reference is set by add() and by nothing else. An Alive pushed straight onto gameObjects has a null world, and when it dies the library logs a warning — "died with REMOVAL but has no world; it stays in play" — and leaves it standing. If you ever see a corpse that will not despawn, that warning is the first thing to search the log for.

2.10SimulationLoop

Most games do want a real-time clock eventually, and writing a correct fixed-timestep loop is a well-known small trap. SimulationLoop is the library's opt-in answer. It spawns one daemon thread that measures real elapsed nanoseconds, converts them into whole ticks at the configured rate, runs those ticks, invokes your onTick callback after each, and parks for half a tick before measuring again.

The interesting part is the accumulator. Real time rarely divides evenly into ticks, so leftover nanoseconds are carried forward rather than discarded, which keeps the simulation's average rate exactly on target instead of drifting. After a stall — a garbage-collection pause, a laptop lid closing, a breakpoint — the accumulator may hold seconds of owed time, and replaying all of it at once would produce a burst of ticks that takes longer to run than the time it represents, which produces more owed time, which is the classic "spiral of death". The guard is maxCatchUpTicks: at most that many ticks run in one call, and anything still owed after the cap is dropped, with a debug line saying how much. The simulation falls behind wall-clock time rather than falling over, which for a game is always the right choice.

Everything runs on the loop thread — both World.tick() and your onTick callback — so the same rule that bare ticking already imposed still holds: do not touch the world from another thread while the loop is running. If you need to feed input in from a network thread, queue it and drain the queue inside onTick.

advance(nanos) is the same logic without the thread, and it is the door out of the loop entirely. A game that already has a render loop, or a test that wants to simulate ninety seconds instantly, can call advance with whatever elapsed time it likes and never call start() at all.

2.11Determinism and the seed

A multiplayer game that cannot reproduce a run cannot debug a desync, and a test suite whose combat outcomes vary run to run is a test suite that will eventually be ignored. So every random decision the engine makes goes through a RandomSource obtained from the world, and a world's source is seeded from a Long you can pin. The default seed is random — a fresh world is a fresh game — but it is logged at info on construction precisely so that any run can be turned into a reproducible one after the fact.

The interface is deliberately tiny: a double in [0,1), a bounded int, and a boolean. Everything the engine needs today (evasion) uses the first; crits, loot tables and spawn jitter will use the others. SeededRandom, the default implementation, is a thin wrapper over kotlin.random.Random, and substituting your own implementation — a recorded sequence for a test, say — is a matter of assigning a different RandomSource where the engine reads one.

One subtlety: an Alive that is not in a world still has to roll for evasion. Rather than reach for a global generator, it lazily builds a fallback source seeded on its own entityId, so even world-less combat in a unit test is reproducible. The seed differs from the world's, so do not expect a unit's rolls to match before and after it joins a world.

2.12Threading

The rule is one sentence long: one world is driven by one thread. Nothing in gametools-core synchronises, and nothing needs to, because the intended topology has a single simulation thread doing all mutation. The event bus makes the same assumption — it is explicitly a single-threaded channel and does no locking of its own.

The networking layer is the exception that proves the rule, and it is careful about it. GameServer holds its player table in a ConcurrentHashMap because WebTools' handshake thread writes to it while the game thread reads it to broadcast, and your onPlayerInput and onPlayerMessage callbacks are invoked on that player's listener thread — not on your simulation thread. The safe pattern, and the one chapter 07 recommends in full, is that those callbacks do nothing but validate and enqueue, and the simulation drains the queue at the top of its own tick.

3.9GameObject: the contract

Everything the engine simulates is a GameObject, and a game object is a remarkably small thing: a position, a flag saying whether it is participating, a per-frame hook, a bag of temporary effects, and a set of things it is able to do. Four fields and a method. Every other class in the library is that idea with something added.

The lifecycle uses the template-method pattern, and the distinction between the two methods matters. tick() is final: it is the frame, and its shape — age the buffs, run the behaviour, retire the expired buffs — is not yours to change. onUpdate() is the hole in it that subclasses fill, and the rule for filling it is to call super.onUpdate() first so that every ancestor's per-frame work still happens. Forgetting that super call is the most common way to break an object in this library: an Alive subclass that omits it silently stops moving, because movement is Actor's contribution to onUpdate.

The ordering inside tick() repays a moment's thought. Buffs age before onUpdate and are pruned after it, which means a buff is fully in force during the update of the last tick of its life, and disappears cleanly at the boundary. This is what makes "durationTicks = n means exactly n updates" true, and it is why a damage-over-time effect written in Buff.onTick ticks a predictable number of times.

active is a hard off-switch rather than a soft one. While it is false, tick() returns immediately: buffs do not age, the object does not move, nothing about it changes. It is the right tool for pooling and for spent projectiles, and the wrong tool for "hidden but still simulating" — that is what VisibleObject.visible is for.

One sharp edge is worth knowing about the position. location is a mutable Point and it is shared: a VisibleObject hands its area's point up to GameObject, so moving the object and moving its drawn area are the same operation by construction, and code that mutates a Point it received from an object is mutating the object. Assign Point(other) when you want a copy — the library does exactly this in Movement.Homing, which builds a fresh point from the target's location every tick rather than aliasing it.

3.10VisibleObject: being drawn

VisibleObject adds the state a renderer needs and no more. It does not draw, does not know what a texture file contains, and does not depend on any graphics library; texture is a string and color is a value object. What the layer really contributes is three ideas.

The first is composition through sub-objects. A health bar, a nameplate, a selection ring or a status icon is not a subclass of anything — it is a plain VisibleObject in another object's subObjects list, drawn in insertion order, snapshotted recursively, and addressable by its own entity id once the world has enrolled it. Alive uses exactly this mechanism for the health bar it ships with, and your own decorations should use it too.

The second is the coupling between active and visible. Deactivating an object also hides it, because an object that is not simulating almost never wants to be drawn — a spent projectile is the canonical case. The reverse is not true: visible can be set on its own, which gives you an object that keeps simulating but is never sent to clients. Fog of war, dormant spawn points and server-side trigger volumes all live in that gap.

The third is angle normalisation. Angles are whole degrees counter-clockwise from the positive x-axis, and the setter wraps anything outside 0..359 into range rather than rejecting it, logging a warning as it does. That policy exists so that callers doing raw angle arithmetic — angle += turnRate — do not have to wrap it themselves. Consistent with the rest of the engine, +y is north; if your renderer's y-axis points down, invert at the boundary, not in the simulation.

Collision at this layer is a centred axis-aligned box test: two objects touch when the gap between their centres is no greater than the summed half-extents on both axes. It is inclusive, so exactly touching counts as a collision and a zero-size box can still hit something — which is what makes a point-like projectile work. It is also open for override, and a subclass that needs circles or rotated bounds should override it rather than reimplementing overlap at every call site.

3.11Actor: getting somewhere

An actor is a visible object that moves under its own power, and the layer's whole design is the separation of how fast from where to from by what rule. Speed is a ModularStat so that hastes and slows can be layered as named mods and peeled off again (chapter 04) rather than folded into one lossy multiplier. Destination is a point. The rule is a Movement value you can swap at runtime.

Assigning destination does three things: it stores the point, it clears the "settled" flag so a stopped Targeting actor resumes, and it re-aims angle at the new point. That last is a one-off computation from the position held at the moment of assignment — the angle is not re-derived as the actor travels, which is exactly right for a sprite that should face the way it was sent and irrelevant for one that does not turn at all. Two cases leave the angle alone: a destination equal to the current position, because there is no direction to face, and a destination holding a NaN, which is logged as a warning.

The step itself is the same in three of the four strategies: if already at the destination, do nothing; if within one step of it, snap exactly onto it; otherwise advance by the locmod vector, which is the direction to the destination scaled to the actor's speed. Snapping is what stops an actor oscillating around a point it can never land on exactly, and it is why isAtDestination can afford to be exact positional equality rather than an epsilon comparison.

The difference between Targeting and Persistent is one boolean. Targeting sets a "settled" flag on arrival and does nothing further until a new destination is assigned, so an actor knocked back from where it stopped stays knocked back. Persistent keeps stepping towards the destination every tick regardless, so the same actor walks back. Choose by asking whether the destination is an instruction that has been completed or a position that must hold. Directional ignores the destination entirely and simply advances along the current angle — it is what DirectionalProjectile is built on. Homing overwrites the destination with the target's live position each tick and then behaves as Persistent.

All movement is gated on the MOVE capability. An actor whose movement has been suppressed by a buff holds its position for that tick, logs a debug line, and keeps its destination and strategy — when the suppression lifts, it resumes where it left off. Rooting a unit is therefore a buff, never a speed of zero.

3.12Alive: health and the health bar

Alive is the largest class in the library because combat genuinely has more moving parts than movement does. Its state divides into six stats, three pieces of identity (world, faction, owner), a small attack state machine, and a health bar.

Health is a CombinedStat — a current amount against a modifiable ceiling — and it is free to go to or below zero, because "depleted" is a state the simulation needs to observe rather than an error to prevent. The other five combat stats are plain ModularStats. All six, plus speed inherited from Actor, are exposed through the stats map under exactly the names a buff addresses them by: "health", "damage", "attackTime", "attackSpeed", "attackRange", "evasion", "speed". That map is a getter rather than a stored field specifically so that reassigning a stat property wholesale — unit.damage = ModularStat(50.0) — keeps working.

The health bar is a small object lesson in avoiding aliasing bugs. It is a red VisibleObject added to subObjects at construction, and it is built from fresh geometry rather than from the constructor's Dimensions and Point, because those instances are shared with the actor itself — sizing the bar from them would resize the actor. Its full width and its vertical offset are captured once at construction, so a unit that is later resized keeps a bar of its original scale; its position is refreshed every tick to follow the actor, and its width is scaled to the current health fraction, clamped into 0..1 so overhealing and negative health both render sanely.

3.13The attack cycle

Combat is a three-state machine driven once per tick, and the states are worth naming precisely. NONE is not fighting. ISSUED means an order exists and the actor is closing the distance: each tick it measures the range to its target and, while the target is further away than attackRange, sets its destination to the target's current position and walks. INPROGRESS means the actor is in range and swinging: progress accrues by attackSpeed / 10000 per tick, and when it reaches attackTime the swing lands, progress resets, and the machine returns to ISSUED — which is what makes the attack a loop rather than a single blow.

Two arithmetic consequences follow. At the defaults a swing takes 1.7 ÷ 0.01 = 170 ticks, which is 8.5 seconds at 20 Hz — deliberately slow, so that a game tuning combat has to choose its own numbers. And "attack speed" is not a rate in hertz but a numerator over a fixed divisor of 10 000; doubling attackSpeed halves the time to a swing, and so does halving attackTime.

Before anything else each tick, the cycle checks whether the target can still be fought. A target whose health has run out ends the attack with TARGET_DIED; a target that once belonged to a world and no longer appears in it (nor in its removal queue) ends it with TARGET_REMOVED. Both fire onAttackEnded(reason) and publish AttackEnded. The check is careful never to fire for a target that was never in a world at all, so combat between two loose objects in a unit test behaves normally.

There are, then, exactly two ways out of the loop, and they are reported differently on purpose. cancelAttack() is the caller's exit — the player pressed stop, the AI changed its mind — and it fires onAttackCancelled and publishes AttackCancelled. It deliberately leaves the actor's destination alone, so a unit that was walking towards its target keeps walking; issue a fresh move order if you want it to stop or retreat. Target loss is the simulation's exit and reports AttackEnded with a reason. A listener that wants "stopped fighting, for any reason" should handle both.

The eleven hooks between onAttackIssued and onDeath exist so a subclass can attach behaviour at each step without reimplementing the machine. They come in symmetric pairs — attacker and target are each told about the same moment — which is what lets a thorns effect (onHitBy), a lifesteal effect (onHitting) and a damage-reduction aura live in different classes without any of them knowing about the others.

3.14Damage, evasion, and who gets the kill

Between a swing and a wound sits one probabilistic gate: the target's evasion is rolled against the world's seeded generator, and on a miss the swing is simply dropped — no hooks, no events, nothing. Because the roll draws from World.rng, a fixed seed reproduces every dodge in a fight exactly; a world-less actor falls back to a generator seeded on its own entity id so that even loose combat replays identically.

Damage that survives the gate passes through calculateDamageTaken, which in the base class returns the incoming amount unchanged. That indirection is where armour, resistances and damage types belong in a game built on this library. The result is subtracted from health.current, the attacker is recorded as the last damager, and DamageDealt is published. Zero damage is skipped entirely, which keeps a mitigated-to-nothing hit from polluting the event stream or stealing kill credit.

Kill attribution is that "last damager" record and nothing more sophisticated. When health runs out, EntityDied carries whoever last removed health as the killer — which is why damage applied by a projectile, or by writing to health.current directly, produces a death with a null killer. If your game needs assist tracking or damage-over-time attribution, listen to DamageDealt and keep the ledger yourself.

3.15Death and respawn

Death is checked at the top of every Alive update: if health is at or below zero and the death has not already been handled, the configured response is applied exactly once. REMOVAL queues the actor into its world's removal list, so it survives to the end of the frame and then leaves cleanly with an EntityRemoved event. RESPAWN moves it to its respawn point, refills its health to the current modified maximum, and clears the guard immediately so it can die again. Either way onDeath() runs and EntityDied is published.

The guard is the detail that makes this reliable. Without it, an actor sitting at zero health would re-trigger its death response on every subsequent tick, filling the removal queue and the event stream with duplicates. With it, one death produces one response, one hook call and one event, and the guard is only re-armed when the actor is genuinely alive again — at which point the last-damager record is cleared too, so a respawned unit's next death is attributed correctly.

3.16Projectiles

Projectile is an abstract actor carrying a flat damage payload and one protected way to apply it. Everything else — what it chases, what counts as a hit, when it expires — belongs to the concrete subclass, of which the library ships two.

HomingProjectile takes a single Alive and a quadtree, sets its movement to home on the target, and each tick asks whether it has actually run into it. That question is answered in two phases: the quadtree returns the objects near the projectile — a window sized to the two bodies' half-extents — and the exact overlap test decides. Testing overlap rather than waiting for the projectile to reach the target's precise coordinates is what makes fast projectiles work at all; a missile moving forty units a tick will step over an exact point almost every time. On impact it deals its damage once, sets a flag so it can never do so twice, and deactivates — which also hides it, so a spent projectile stops both simulating and being broadcast.

DirectionalProjectile flies along a fixed heading for a bounded number of ticks and damages every Alive it passes through, keeping a set of the ones it has already hit so each is hurt exactly once. That is what makes it pierce a line of targets. Its broad-phase window defaults to three times its own width, which is a sensible default for a projectile moving at ordinary speeds; a very fast or very small projectile should pass a larger searchRadius, because neither projectile performs swept-volume collision and both can tunnel through a target if they move further in one tick than the search window is wide.

Both classes take the quadtree as a constructor argument and expect the caller to keep it current — the same clear-and-refill that World.tick() already performs once per frame. Passing world.quadtree is the normal thing to do. Note that projectile damage bypasses the Alive combat pipeline entirely: it is subtracted straight from health, so it raises no DamageDealt event, triggers no onDamaged hook, and leaves no killer to attribute. If projectile kills need to be credited in your game, publish your own event from a subclass hook.

3.17Player and ownership

A Player is a roster with a name. Its single job is to make "which units are mine?" a cheap question and to keep that answer consistent with each unit's own view of who owns it.

The invariant is that Alive.owner and Player.ownedAlives never disagree, and it is enforced in the property setter rather than in the roster methods. Assigning an owner removes the actor from its previous owner's roster and adds it to the new one; own() and disown() are conveniences that drive the same property and report whether anything actually changed. The roster-mutating methods are internal, so there is no supported way to get the two views out of step. An actor is on at most one roster at any moment — this is single ownership, not shared control.

Finally, a naming trap worth repeating: this Player has nothing to do with the players a GameServer tracks. One is a game-domain owner of units; the other is a name a connection handshook with. A game will usually maintain a map between them, and that map is your code's responsibility, not the library's.

4.7Why stats are objects

The naïve way to hold a unit's speed is a Double. It works until the first potion, at which point somebody writes speed *= 1.2 and the game acquires a permanent, untraceable bug: when the potion expires the code divides by 1.2, floating-point rounding leaves a residue, a second effect applied in between shifts the base, and after an hour of play every unit's speed is slightly wrong with no way to find out why.

The fix is to stop storing the result and start storing the reasons. A ModularStat keeps an immutable-by-convention base and a list of named modifiers, and recomputes its effective value from scratch whenever that list changes. Removing a modifier is not an inverse operation applied to a number; it is the deletion of a list entry followed by a recomputation. There is no drift, because nothing is ever undone — it is only ever recalculated.

The interface is Moddable, implemented by both stat types, and it is what lets GameObject.stats expose a heterogeneous map of stats by name without the caller knowing which kind each one is. A buff addressing "health" and a buff addressing "damage" are written identically even though one targets a current/max pair and the other a single value.

Both stat types also carry a full set of arithmetic and comparison operators against Double, against each other, and — through top-level extension operators — with a Double on the left. That is why if (distance > attackRange) and health.current -= damage.value read as ordinary arithmetic. It is sugar, but it is the sugar that makes the abstraction worth adopting: a stat that is awkward at the call site gets bypassed, and a bypassed stat is a bug waiting to be written.

4.8The two multiplicative stackings

Most of the subtlety in the stat system lives in one distinction that games get wrong constantly: whether two +20% bonuses make +40% or +44%.

Modifiers with additive stacking sum into a single bonus applied on top of 1.0, so 0.2 and 0.1 together give ×1.3. This is how most players expect gear and potions to combine, and it degrades gracefully — the tenth bonus is worth exactly as much as the first. Modifiers with multiplicative stacking have their factors multiplied together, so 1.2 and 1.1 give ×1.32. This is how "independent" or "final" multipliers behave, and it compounds — stacking many of them explodes.

The two pools are computed separately and then combined: the summed bonus forms one factor, the product of the multiplicative factors forms another, and the stat's base is scaled by both before any flat modifiers are added. Note the difference in what value means between the two: 0.2 in an additive-stacking mod is a bonus fraction, while 1.2 in a multiplicative-stacking mod is a factor. Mixing the conventions is the single easiest mistake to make here; a mod of 1.2 with additive stacking is a +120% bonus, not a +20% one.

Flat modifiers are always added last, after all scaling, which makes "+5 damage" mean exactly five damage regardless of what percentage bonuses are in play. That ordering is a design decision worth knowing when you tune: percentage bonuses never amplify flat ones.

SETTING and INCREMENTING are a different axis — they control what happens when a mod of a name that is already applied is applied again. SETTING overwrites the existing value, which models a refreshable effect whose strength does not grow. INCREMENTING adds to it, which models a stacking charge. Both add the mod if none of that name exists yet. NONE is inert by design: a placeholder mod that participates in nothing.

4.9CombinedStat and the rescaling rule

Health, mana and stamina all have the same shape: a current amount that changes constantly, and a maximum that changes rarely but must itself be modifiable. CombinedStat is that pair, with the maximum held as a full ModularStat so the ceiling gets the whole modifier system while the current amount stays a plain, fast Double.

The important behaviour is what happens when the ceiling moves. Applying a mod to a CombinedStat captures the current fraction, changes the maximum, and then moves the current amount so that fraction still holds. A unit at half health that gains a +100% maximum-health buff ends up at half of the new maximum — 100 / 200 — rather than at 50 / 200, and when the buff expires it returns to 50 / 100. Neither application nor expiry is a heal or a wound. The alternative policies both have obvious failure modes: preserving the absolute current value means a big max-health buff effectively wounds the unit as a fraction, and topping up to full means the buff is a free heal that can be cycled.

Deliberately, current is not clamped. It may exceed the maximum (overheal, shields) and it may go to or below zero, which is exactly what Alive.isAlive tests and what lets a killing blow's overkill be measured. fractionOfMax is likewise unclamped and may leave 0..1; consumers that render a bar clamp at the point of rendering, as the built-in health bar does.

4.10Buffs

A buff is a bundle: a name, a duration in ticks, a map from stat name to modifier, and a set of capabilities to hold down. Attaching it applies each modifier to the matching stat, records the suppressions and fires onApplied. From then on the owning object's tick drives it — firing onTick, counting the duration down, and removing it when it reaches zero, at which point the modifiers are reverted, the capabilities freed and onExpired fired.

Two details govern how long "the duration" really is. Buffs age before the object's update and are pruned after it, so a buff created with durationTicks = n is in force for exactly n updates and its onTick fires exactly n times. And a negative duration never counts down, which is the idiom for an indefinite effect — an aura, a permanent curse — removed explicitly with removeBuff or dispel.

A modifier whose key the object does not expose is skipped with a warning rather than throwing. This keeps one bad buff from taking down a tick, but it also means a typo in a stat name produces an effect that silently does nothing — if a buff appears inert, search the log for "targets unknown stat" first.

Stacking between buffs is deliberately not solved by the library, because the right answer is game-specific. What the library guarantees is the mechanism: modifiers are removed by name, so two buffs whose modifiers share a name share fate, and a capability stays suppressed while any active buff lists it, so overlapping suppressors resolve correctly with no work on your part. Two stuns that overlap behave sensibly by construction; two hastes that both call their modifier "haste" do not. Namespace your modifier names by the buff that owns them and the problem disappears.

Subclassing Buff is how behaviour beyond stat arithmetic is expressed. A damage-over-time effect subtracts health in onTick; a visual cue attaches a sub-object in onApplied and removes it in onExpired; a "on expiry, explode" effect spawns something in onExpired. The hooks receive the target, so a buff never needs to capture it.

4.11Capabilities

Every game eventually needs to say "this unit cannot move right now", and the tempting implementations are all bad. Setting speed to zero loses the original speed and interacts badly with slows. A canMove boolean does not compose — two overlapping stuns, one ending, leaves the unit unrooted while the other is still active. A counter composes but has to be maintained by hand.

Capabilities are the library's answer. A type declares what it inherently can do — Actor adds MOVE, Alive adds ATTACK, each as super.capabilities + … — and can(capability) answers whether it is usable at this instant: the type must have it, and no active buff may list it as suppressed. Because the answer is derived from the live set of buffs rather than stored, overlapping suppressors need no reference counting. When the last stun expires, the capability returns; while any remains, it does not.

The built-in layers gate their own per-tick work on exactly this, and the gating is a freeze rather than a cancel. A rooted actor keeps its destination and strategy and resumes when the root lifts; a disarmed Alive keeps its attack order and its target, with swing progress held where it is, while death handling and the health bar carry on as normal. Your own subclasses should follow the same pattern: declare the capability, gate the work, and let buffs do the suppressing.

The one hard requirement is that a capability's id is stable and unique, because the id — not the object — is what crosses the wire inside a BuffSnapshot so that a client can grey out a disabled ability. Two capabilities sharing an id will be confused on the client.

4.12How combat uses all of this

Chapter 03 describes the attack loop as a state machine; it is worth restating it here as an exercise in the stat system, because every number in the loop is a modifiable stat and therefore every number is a legitimate target for a buff.

attackRange decides when the approach ends and the swing begins, so a buff can extend a melee unit's reach. attackSpeed and attackTime together decide how long a swing takes — progress accrues at attackSpeed / 10000 per tick and must reach attackTime — so a haste can be modelled at either end. evasion is the probability the swing is dropped, rolled against the world's seeded generator. damage is the amount removed on a hit, and health is what it is removed from. Seven stats, one loop, and every one of them addressable by name from a buff without Alive knowing that buffs exist.

4.13Pitfalls

Reassigning a stat wholesale drops its modifiers. unit.damage = ModularStat(50.0) replaces the object, and any modifiers applied to the old one go with it — including modifiers owned by buffs that are still active and will later try to remove them. Prefer unit.damage.base = 50.0 for a permanent change.

Shared modifier names share fate. Stated twice because it is the bug you will actually hit.

A mod's value is mutable and shared. StatMod is a data class with a var value, and INCREMENTING stacking mutates the applied instance. Do not reuse one StatMod instance across several objects unless you intend them to share it.

Negative values are not rejected anywhere. A negative speed runs an actor backwards, a negative damage heals, an evasion above 1.0 dodges everything. The library treats these as your business, not as errors.

Apply buffs after construction. applyBuff reads the object's stats and capabilities, so it must run once the object is fully built — never from inside a constructor that a subclass has not finished running.

5.1The structure

Each node stores one point and one element, and splits the rest of the plane into four quadrants about that point. Not a bucketed grid, not a balanced tree: the first element inserted becomes the root, and insertion order alone decides the shape.

5.6Why an index at all

"Which objects are near this one?" is the question a game asks most often and the one that is easiest to answer catastrophically. Asked naïvely — compare every object with every other — it costs a quadratic number of comparisons, so a hundred objects cost ten thousand tests per frame and a thousand objects cost a million. The frame budget disappears into distance arithmetic long before the game gets interesting.

A spatial index trades a little bookkeeping for the ability to discard most of the world without looking at it. The quadtree here is the classic point-region variety: each node holds one point, and the four subtrees hold everything in the four quadrants around it. A query for a rectangular window descends only into the quadrants the window actually overlaps, so a small window in a large world touches a logarithmic number of nodes.

5.7Structure and the cost of simplicity

The implementation is deliberately plain — it is a direct port of an older engine's tree — and its simplicity has one consequence you must design around: it is unbalanced. There is no rotation, no splitting threshold, no re-partitioning. The first point inserted becomes the root and every subsequent point is placed relative to it. Insert points in sorted order and the tree becomes a linked list with a logarithmic-looking API and linear behaviour.

In practice this rarely bites, for a reason worth understanding: the engine rebuilds the tree from the object list every frame, and objects in a game world are scattered rather than sorted, so the shape that emerges is close enough to balanced. If you ever build a tree of your own from data that is ordered — a grid of terrain tiles, say, generated row by row — shuffle before inserting.

5.8Query semantics

retrieveBox returns elements whose points lie inside the window; it knows nothing about their sizes. That is the correct division of labour for a broad phase — the index answers "roughly where", the caller answers "actually touching" — but it means the window must be sized to account for the extents of the things you are looking for. A window exactly as wide as a projectile will miss a target whose centre is just outside it but whose body overlaps. The two built-in projectiles size their windows accordingly: the homing one from the summed half-extents of both bodies, the directional one from a searchRadius that defaults to three times its own width.

The window is also half-open — the minimum bounds are exclusive, the maximum bounds inclusive — which is an artefact of the comparison logic rather than a considered API choice, but it is stable behaviour and worth remembering when a test asserts on an object sitting exactly on a boundary.

Actor.nearby is the convenience wrapper: it builds a square window of a given half-extent around the actor and queries with it. Note that the actor is included in its own results when it is itself in the tree, so filter yourself out before acting on the list — every collision check in the library ends up doing this implicitly by looking for a specific type or target.

5.9Rebuild versus mutate

Two strategies exist for keeping a spatial index current: update it as objects move, or throw it away and rebuild it. GameTools rebuilds, at the top of every tick, and the reasoning is that in a game where most objects move most frames, an incremental update pays a removal and an insertion per moved object anyway — plus the bookkeeping to remember where each object was last indexed, plus the tombstone accumulation this particular implementation would suffer. A rebuild is one pass with no state to get wrong.

The cost of that choice is the staleness noted in chapter 02: the index reflects the positions objects held when the frame began, so a query made late in the frame can be up to one tick of movement out of date. For broad-phase use, where the window is generous and the narrow phase runs against live positions, this is invisible. For anything that needs exact current positions — an authoritative hit registration, say — do not ask the index; ask the objects.

5.10The broad-phase / narrow-phase pattern

Every proximity check in the library follows the same two-step shape, and yours should too. The broad phase asks the index for candidates within a generous window; it is cheap and approximate, and it is allowed to return things that are not actually touching. The narrow phase runs the exact test — normally collidesWith — on the handful that survived, and it is exact and comparatively expensive. Skipping the broad phase makes the check quadratic; skipping the narrow phase makes it wrong.

Neither phase is swept. A projectile that moves further in one tick than the combined extents of itself and its target can pass entirely through without a frame in which the two overlap. If you are firing fast projectiles, either raise the tick rate, lower the speed, enlarge the projectile's bounds, or implement a swept test in a collidesWith override.

5.11Using the tree directly

Nothing about Quadtree is specific to game objects. It is generic in its coordinate type (anything Comparable) and its element type, so it will happily index waypoints by integer grid coordinates, or points of interest by BigDecimal. If you build your own, you own its lifecycle: decide whether to rebuild or to mutate, remember that remove matches by identity on the path to the coordinates you supply, and keep one tree to one thread.

6.5What the bus is for

Without an event bus, every system that cares about combat has to be reachable from the combat code. The score counter gets a reference passed into Alive; the networking layer gets another; the aggro system gets a third; and Alive, which should know about health and swing timers, ends up knowing about scoring, sockets and AI. The bus inverts that: combat announces what happened, and whoever cares subscribes.

The design constraints follow from where the events are published — in the middle of a tick, on the simulation thread. That rules out an asynchronous bus (a listener that runs later sees a world that has already moved on) and it rules out anything that allocates or locks heavily per event. What is left is a list of listeners and a loop, which is exactly what EventBus is.

6.6Delivery semantics

Publishing appends the event to an internal queue and, if no delivery pass is already running, starts one that drains the queue completely before returning. That single mechanism gives two properties at once. Ordinary publication is synchronous — by the time publish returns, every listener has seen the event. And re-entrant publication is flattened: a listener that publishes in response to an event does not recurse; its event joins the queue and is delivered once the current one has finished reaching everybody. The stack stays flat no matter how many listeners cascade, and the delivery order stays a deterministic breadth-first walk rather than depth-first recursion.

Each pass iterates over a copy of the listener list, so subscribing or cancelling from inside a listener is safe: the change takes effect for the next event, not the one being delivered. Each listener call is wrapped so that a thrown exception is caught, logged with the event that caused it, and stepped over. That is a deliberate trade — a buggy listener degrades one feature rather than halting the simulation — and it means your listeners must not use exceptions for control flow, because nothing above will ever see them.

The bus does no synchronisation. It is documented as single-threaded and it assumes the same topology the tick already requires: one world, one thread. If a network thread needs to inject an event, hand the data to the simulation thread and publish from there.

6.7Reading the catalogue correctly

The eight events divide into two lifecycle events and six combat events, and the pairs within them are worth distinguishing carefully.

EntitySpawned and EntityRemoved bracket an object's membership of a world, not its existence. An object that is constructed and never added raises nothing; an object removed and later re-added raises a second spawn, because the world forgets its announcement when it leaves. Sub-objects — health bars, nameplates — are indexed so they can be addressed by id, but they are never announced: they are part of their parent's arrival, not independent ones.

AttackCancelled and AttackEnded both mean "stopped attacking" and are separated by who decided. Cancellation is external — your code, a player, an AI. Ending is internal — the target died or left. A listener that wants to know the unit is idle should handle both; a listener implementing "attack the next enemy when this one dies" wants only AttackEnded with reason TARGET_DIED.

AttackLanded and DamageDealt are also two views of one moment, and here the distinction is scope. AttackLanded is specific to the attack loop and carries the attacker's damage stat. DamageDealt is the general "health was removed" signal, carries the amount actually applied after mitigation, and permits a null source — it is the event to build a damage meter on. Note that neither fires for damage a projectile deals, which goes straight to health.

6.8Patterns

Scoring and statistics. Subscribe once at startup, keep your counters in the listener, and never touch the combat code. EntityDied gives kills, DamageDealt gives a damage meter, and the pair together gives assists if you keep a short window of recent damagers.

The network bridge. A listener that turns EntitySpawned and EntityRemoved into explicit "unit appeared" and "unit vanished" messages lets a client stop inferring lifecycle from diffing successive state broadcasts, which is both cheaper and less error-prone.

Reactive AI. Aggro is naturally an event listener: on DamageDealt, if the target is mine and it is not already fighting, issue an attack at the source. Written this way it lives in one place instead of being threaded through the combat hooks.

Deferred work. Because delivery is synchronous and inside the tick, a listener that wants to change the world should usually queue the change and apply it at a frame boundary rather than mutating from inside delivery.

6.9Hooks or events?

The library offers two extension mechanisms for the same moments, and choosing between them is straightforward. Override a protected hook — onHitBy, onDeath — when the behaviour belongs to that kind of unit: a thorns aura, a boss's enrage at half health, a unit that explodes when killed. Subscribe to an event when the behaviour belongs to a system that spans units: scoring, networking, telemetry, achievements. Hooks need a subclass and see one object; listeners need nothing and see everything.

6.10Pitfalls

Listeners are called on the simulation thread, inside the tick. Anything slow — a disk write, a blocking send, a database call — stalls the frame for every listener behind it and the rest of the world with it. Buffer and flush elsewhere.

Exceptions vanish. They are logged at warn with the offending event and then swallowed. If a listener has silently stopped working, that log line is the place to look.

Subscriptions are strong references. The bus holds every listener until cancel() is called; a listener capturing a large object graph keeps it alive. Cancel when the subscriber's own lifetime ends.

Events carry live objects, not copies. The entity in an EntityDied is the actual actor, and by the time you read it later it may have respawned or been removed. Extract what you need during delivery.

7.6The transport model

GameServer is a thin, opinionated layer over Spartan Laboratories' MultiConnectionUDPServer. The base class owns everything socket-shaped: it binds one fixed common port, listens for handshakes, replies to them, and multiplexes every subsequent datagram — application traffic, state broadcasts and keepalives alike — over that same shared socket. GameServer supplies the game-specific half: a connection cap, verb routing, and JSON serialisation of world state.

The single-socket design is what makes the server NAT-traversable end to end, and it is worth understanding why. A server that answers a handshake by opening a fresh port pair for that client creates a mapping the client's NAT has never seen traffic on, and the first datagram from the new port is dropped. Answering from the same socket the handshake arrived on, addressed back to the datagram's own source address and port, reuses the mapping the client's NAT has already created. The cost is that the mapping expires when it goes quiet, which is why the protocol requires a bare KA keepalive from the client roughly every twenty seconds. WebTools consumes those silently; they never reach your callbacks and you never need to think about them beyond making the client send them.

Everything is UDP, and UDP's properties are yours to live with: datagrams may be lost, duplicated or reordered, and there is no delivery guarantee anywhere in the stack. For state broadcast this is the right trade — a lost frame is superseded by the next one a moment later, and a reliability layer would only add latency to data that is already stale. For anything that must arrive, you need your own acknowledgement scheme on top; the library does not provide one.

7.7Handshake, admission and reconnection

By the time GameServer is consulted, the base class has already replied REGISTERED to the client. That ordering has a consequence that surprises people: a refusal cannot be expressed as a rejected handshake. What happens instead is that the connection is terminated, which unbinds its message handler, and the refused client is left believing it is connected while nothing on the server ever answers it again. If your client needs to distinguish "full" from "the network ate my packets", you will need an application-level acknowledgement — a first STATE frame is the usual signal.

Admission itself has three outcomes. A handshake that arrives before the subclass has finished constructing is refused — the base class starts accepting from its own init block, which the JVM runs before subclass fields are assigned, so a client already retrying Iam when the server boots can reach onClientConnect while the player table is still null. That window is detected explicitly and refused rather than left to fail on the handshake thread. A handshake that would exceed maxConnections is refused. Everything else is admitted.

Reconnection is handled specially and deliberately. A player handshaking under a name that is already connected is always admitted — they replace their previous connection rather than counting a second time against the cap — and the stale connection is terminated so it stops holding a message handler. This is what makes recovery from a dropped NAT mapping work: the client simply handshakes again, from whatever address it now has, and carries on. It also means that names are identity on this server, and that anybody who knows a player's name can evict them by handshaking with it. If that matters to your game, authenticate names in onPlayerMessage before acting on anything.

7.8Routing

Every datagram from an admitted player is split at the first space into a verb and a remainder. A verb of INPUT has its remainder decoded as a MouseAction; on success your onPlayerInput receives the player's name and the decoded action, and on failure the payload is logged at warn and dropped without reaching either callback. Every other message is trimmed and passed verbatim to onPlayerMessage, again with the sender's name.

That fall-through is the extension point for your own protocol. Chat, ability commands, unit orders and lobby traffic all arrive as raw strings tagged with a player name, and you parse them however you like. The one reserved word is INPUT; STATE is only ever sent by the server, and KA never reaches you.

Note what the name in these callbacks is and is not. It is the name the sender handshook with — the server's identity for a connection. It is not a game-domain Player, and the library maintains no mapping between the two. Keeping that map is your code's job, and it is the natural place to enforce that a command only moves units its sender owns.

7.9Broadcasting state

broadcast comes in two forms. The convenience form takes any iterable of VisibleObjects, filters out the invisible ones, snapshots each as the most specific kind that fits, and sends the lot. The explicit form takes snapshots you have already taken, which is what you want if you are filtering per player — culling by distance, hiding fog-of-war units, or sending different views to different people. Both encode to a single JSON array and send it as one STATE datagram to every currently tracked player.

Three practical limits deserve attention. First, visibility filtering is not per player: the built-in path sends the same array to everyone, so anything a client should not know must be excluded before it reaches broadcast — with the explicit form and a per-player snapshot list. Second, a datagram has a practical size limit of about a kilobyte and a half before IP fragmentation, and a hundred fully-populated snapshots will exceed it; a large world needs interest management (send only what is near each player) rather than a bigger buffer. Third, broadcast rate is your choice and should usually be lower than the tick rate — every second tick at 20 Hz gives 10 frames a second on the wire, which is plenty for a client that interpolates.

Every send returns a Result, and pushToAllPlayers is careful to attempt delivery to every player regardless of earlier failures, folding the outcomes so that only the reported result short-circuits. One unreachable player never costs the others their frame.

7.10Threading

This is the part of the library where threads genuinely exist, and the contract is worth stating precisely. WebTools runs a handshake thread and, for each admitted player, a listener thread. Your onPlayerMessage and onPlayerInput callbacks run on that player's listener thread. They may therefore run concurrently with each other, concurrently with your simulation, and concurrently with your own calls to broadcast. The player table itself is a ConcurrentHashMap precisely because the handshake thread writes it while the game thread reads it.

None of that concurrency extends to the simulation, which is single-threaded and unsynchronised. So the rule is absolute: a callback must never touch the world. Validate the input, wrap it in a command object, put it on a concurrent queue, and return. Drain that queue at the top of your tick — the onTick callback of a SimulationLoop is the natural place — and apply the commands there, on the simulation thread, where mutation is safe.

The same applies in reverse: broadcast reads live objects while it snapshots them, so calling it from a thread other than the simulation's races with the tick. Broadcast from onTick, or from your own loop after tick() returns.

7.11Lifecycle

Construction starts the server. There is no start(): the base class spawns its handshake thread from its own initialiser, so a client may connect before the constructor's caller has assigned the reference. Build the server after everything it needs is in place, and be aware that the "handshake arrived too early" refusal exists because this ordering is genuinely observable in production.

Because the common port is fixed, exactly one instance can exist per JVM at a time — a second constructed before the first is shut down will fail to bind. This is also why the build serialises every test task that starts a server behind a single-permit shared service.

shutDown() is the correct teardown: it forgets the players and then performs the inherited stop, which tears down every registration and releases the port. Calling the inherited stop() directly leaves this class's player table populated. Once shut down, an instance is finished; there is no restart, and you construct a new one.

7.12What the client must do

The library ships no client, so the obligations of one are worth listing. It must send Iam <name> to the common port and wait for REGISTERED. It must send every subsequent datagram from the same socket, since that is the mapping the server replies to. It must send a bare KA on an idle interval of roughly twenty seconds. It should encode input as INPUT <json> — GameServer.inputMessage(action) builds exactly the right string, and is public so a Kotlin client can share it. And it must decode STATE payloads polymorphically, keyed on each entry's type field, which chapter 08 describes in full.

7.13What is deliberately absent

There is no encryption, no authentication, no reliability layer, no delta compression, no interest management and no client-side prediction. Each of those is a real requirement for a shipping game and each is a design decision that belongs to the game rather than to a transport shim. What the library guarantees is that a name-tagged datagram reaches your code and that a list of objects reaches the client; everything above that line is yours.

8.5Why snapshots exist at all

The alternative to snapshots is annotating the live classes and sending them directly, and it fails for three separate reasons. Live objects are mutable and are being mutated by the simulation thread while the serialiser walks them. They contain state a client has no business seeing — a world back-reference, an attack state machine, an owner object that would drag its whole roster along. And they are cyclic: an Alive points at its Player, which points back at its roster.

A snapshot cuts all three problems at once. It is an immutable data class taken at a single instant, it contains exactly the fields a client needs, and it flattens references into values — an owner becomes a name, a stat becomes a number, a live point becomes two doubles. Taking one is the moment of consistency; everything after it is a value that can be encoded, queued or logged at leisure.

8.6Shape follows inheritance

Each layer of the object model has its own snapshot type, and each nests the layer below it rather than copying its fields. An AliveSnapshot holds an ActorSnapshot, which holds a VisibleObjectSnapshot, which holds a GameObjectSnapshot. The wire format therefore mirrors the class hierarchy exactly, and adding a field to a layer means touching precisely one snapshot type — which lives in the same file, immediately below the class it copies, so the omission is visible.

The three drawable snapshots share the DrawableSnapshot sealed interface, which requires only two things of them: a stable id and a list of sub-object snapshots. Those two are what a client needs generically — the id to track an object across frames, the sub-objects to draw its decorations — and everything else is reached by matching on the concrete type.

DrawableSnapshot from obj picks the most specific kind that fits, testing Alive before Actor before the plain case, so a mixed list of world objects snapshots correctly with no type analysis on your part. Because the interface is sealed, kotlinx serialises it polymorphically: each entry carries a type discriminator, and a client decoding the array gets each object back as the right kind.

8.7What is captured, and when

Stats are captured as their effective values, with every applied modifier already folded in. A unit under a +30% haste reports its hastened speed, not its base and a list of modifiers. That is deliberate: a client renders and predicts, it does not recompute stat arithmetic, and sending the modifier list would oblige it to implement the whole stacking system correctly.

Buffs are the exception, and only partly. Each active buff is captured as its name, its remaining duration and the ids of the capabilities it is suppressing — which is exactly what a client needs to draw a buff timer and grey out a disabled ability, and no more. The modifiers themselves are not sent, because their effect is already visible in the stat values.

Sub-objects are snapshotted recursively and filtered by visibility on the way, so an invisible health bar on a visible unit is simply absent from the payload rather than sent and hidden. The same filtering happens at the top level in the convenience broadcast overload: an invisible object is never mentioned to a client at all, which is the mechanism behind server-side-only entities.

8.8Identity on the wire

Before 3.1 a client had to track objects by their position in the broadcast array, which breaks the moment anything spawns or dies. Every drawable snapshot now carries the object's EntityId.raw, so a client can keep a map from id to its own view object and match frames to it regardless of ordering or size changes.

Zero means "not addressable", and it arises in two ways that a client can treat identically: the object had no world when it was snapshotted, or the payload predates 3.1 and carried no id at all. Sub-objects carry ids too, since the world enrols them, so a health bar is individually addressable if you ever need it to be.

8.9Decoding on the client

A Kotlin client shares the types and decodes the array directly as a List<DrawableSnapshot>, matching on the concrete kind. A client in another language keys on the type discriminator — "alive", "actor", "visibleObject" — and reads the nested objects by name. Either way the recommended shape is the same: keep a map from entity id to your own render object, update the ones present in the frame, and retire the ones that have not appeared for a few frames.

Interpolation matters more than it looks. At a broadcast rate of ten frames a second, drawing positions exactly as they arrive produces visible stepping; interpolating between the last two known positions, one frame behind, is the standard fix and costs nothing but a little buffering. The turns flag tells you whether angle is worth applying at all, and health's current and max are enough to draw a bar without the server sending one — although the server does send one, as a sub-object, for clients that would rather not.

8.10Evolving the format

The compatibility rule the library follows is the one kotlinx-serialization makes cheap: new fields arrive with defaults. A field with a default is optional on decode, so an old payload loads and the new field takes its default value; and because the encoder omits defaults, a field left at its default costs nothing on the wire either. Both 3.1 additions — the entity id and the buff list — were made this way, which is why a 3.0 client and a 3.1 server still interoperate at the 3.0 feature level.

Removing or renaming a field, or changing its type, is a breaking change with no such escape hatch. If it must happen, add the replacement alongside the original, migrate clients, and remove the original in a later major version.

9.7Where the library expects you to extend it

Kotlin classes are final unless declared open, so the library's inheritance surface is exactly the set of types and members it chose to open. That set is small and it is a design statement: these are the seams, and everything else is either an implementation detail or a place where composition is the intended answer.

Open classes. VisibleObject, Actor and Alive are open, as is Buff; GameObject and Projectile are abstract and must be subclassed. World, Player, EventBus, SimulationLoop, Quadtree, GameServer and both concrete projectiles are final — extend them by wrapping or by listening, not by subclassing.

Open members. onUpdate() is the per-frame seam on every object; collidesWith is the geometry seam; active is open because VisibleObject needs to couple it to visibility; capabilities and stats are open so each layer can extend its predecessor's set; Alive's eleven combat hooks and die() are the combat seams; and Buff's three lifecycle hooks are the effect seams. That is the complete list.

Interfaces to implement. Capability for new abilities, RandomSource for a different generator (a recorded sequence in a test, a network-synchronised one in a lockstep game), Moddable if you invent a stat type of your own, and EventBus.Listener — although that is a fun interface, so a lambda is the normal way to write one.

What internal means here. A handful of members — Actor.hasSettled, Actor.move, stepTowardsDestination, stepAlongAngle, Player.addToRoster, entityId's setter, ModularStat.value's setter — are visible within the module and to nobody else. They are documented in this folder because the behaviours they implement are observable, but they are not API: they may change without a major version, and your code cannot call them.
